## Installation, Discovery und MCP-Aufruf

Nachgewiesen im Job „Release-Artefakt (frische Installation)“ auf einem frischen
GitHub-Actions-Runner mit eigener Datenbank, getrennt vom PHPUnit-Job:

1. `npm run build:native-release` baut das ZIP. Das Build-Skript bricht ab, wenn
   die Komponente nicht `local_coursepilot` heißt, `LICENSE` nicht AGPL-3.0 ist,
   `lang/de/` enthalten ist oder `lang/en/` fehlt. `NOTICE` wird mitgeliefert.
2. Genau dieses ZIP wird entpackt und als Plugin in eine frische Moodle-Instanz
   installiert, die Site wird installiert.
3. `scripts/ci/verify-native-artifact.php` prüft:
   - Registrierung von `local_coursepilot_get_version_info` und Zugehörigkeit
     zum Dienst `coursepilot`;
   - einen Webservice-Aufruf durch einen Nutzer, der nur
     `local/coursepilot:useremote` besitzt;
   - den MCP-Weg: OAuth-Client per DCR, Autorisierungscode mit PKCE,
     Code-Einlösung → Access-Token; ohne Token `401`; mit Token
     `server/discover` (`serverInfo.name = local_coursepilot`), `tools/list`
     (49 Werkzeuge, darunter `coursepilot_get_version_info`) und `tools/call`.
     Der Nutzer wird dabei nur über das Token bestimmt.
   - Versionskonsistenz: Handshake, Werkzeugantwort und installierte
     Datenbankversion entsprechen `version.php` des ZIPs (`2.0.0-alpha`,
     `2026092301`).

Log-Ausgabe: `OK: MCP ueber OAuth - server/discover, tools/list (49 Werkzeuge),
tools/call coursepilot_get_version_info -> 2.0.0-alpha (2026092301), Moodle
5.0.10+ (Build: 20260928).`

Grenze des Nachweises: Die MCP-Anfragen laufen über `dispatcher::handle()`, die
Seam, an die `mcp.php` den HTTP-Rumpf übergibt. Nicht automatisch geprüft sind
der HTTP-Transport selbst (Bearer-Header-Parsing in `mcp.php`), die
Well-Known-Discovery nach RFC 8414/9728 über den Webserver und der
Zustimmungsdialog im Browser. Genau diese Strecke deckt der Praxistest mit einem
echten KI-Client ab.

Keine laufende Kurs- oder Praxistestinstanz wurde durch die Abnahme verändert;
alle Nachweise stammen aus frischen CI-Instanzen. Hinweis: Zum Auffinden der
Notice lief die PHPUnit-Suite zusätzlich im Spike-Container gegen dessen
getrennte Test-Datenbank (`t_`). `scripts/phpunit.sh` spiegelt dabei den
Branch-Stand in den Plugin-Ordner der Spike-Instanz; der Code dort entspricht
damit dem Branch einschließlich der `active_tokens()`-Korrektur. Version,
Datenbankschema und Spike-Daten blieben unverändert, `upgrade.php` lief nicht.
