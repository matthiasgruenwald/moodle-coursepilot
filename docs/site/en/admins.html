Installation and operation

For you if you set up and run Coursepilot (local_coursepilot) on a Moodle site. Teachers then connect their AI client themselves; see the teacher guide.

Requirements Installation Remote access Settings OAuth Site check Kill switch and revocation WebDAV Data protection Language pack

Maturity

Coursepilot is a beta (version 2.1.2-beta, Moodle maturity MATURITY_BETA). It runs in the author's own teaching; production use at another school is still to come. Known limits are listed on the developer page.

Installation

  1. Unpack the plugin ZIP into local/coursepilot or upload it via "Install plugins".
  2. Run admin/cli/upgrade.php or confirm the upgrade in the web interface. This registers the web service functions (service "Coursepilot") and the capabilities.
  3. Enable web services and the REST protocol, if you haven't already: Site administration › Server › Web services › Overview, step 1 "Enable web services" and step 2 "Enable protocols" (REST).
  4. Grant teachers remote access (next section).
  5. Open the site check and make sure all three requirements are met.

After every update: Run upgrade.php again. If capabilities or web service functions have changed, course navigation and tool calls otherwise fail with HTTP 500.

Grant remote access

A teacher can only connect their AI client once you've granted them remote access. Being enrolled as a teacher in a course isn't enough. Coursepilot creates neither a cohort nor a role for this. There are two routes:

  1. Cohort (recommended): In the plugin settings, pick one or more existing system cohorts under Remote access cohorts, e.g. the cohort your school already maintains for its teachers. Cohorts of a course category can't be selected.
  2. Existing system role: Allow local/coursepilot:useremote in a role assigned at system level: Site administration › Users › Permissions › Define roles › click the pencil icon ✎ "Edit" next to the role, filter for useremote, set "Allow". The capability has no default, so a system-wide teacher role doesn't bring remote access along by accident. Don't allow it in "Authenticated user", or students get remote access too.

Access is checked on every call. Anyone removed from the cohort or losing the role is turned away on their next call, even over an existing connection. Remote access grants no course permissions: nobody gains access to other people's courses through it. "Check permissions" in Moodle only shows the role route, not cohort membership.

OAuth and clients

Each teacher connects their AI client themselves: enter the endpoint https://<moodle>/local/coursepilot/mcp.php, sign in once, and allow the connection on the Moodle page "Connect Coursepilot". No token is ever passed around by hand.

  • Method: OAuth 2.1 with PKCE, discovery per RFC 8414/9728. Clients register themselves, via Dynamic Client Registration (RFC 7591) or Client ID Metadata Document (CIMD). There is no list of pre-registered clients.
  • Lifetimes: authorization code 120 seconds, access token 1 hour, refresh token 30 days.
  • Browser origin: If a request carries an Origin header, only the site's own address, https://claude.ai and https://chatgpt.com are allowed. Requests without Origin (e.g. from Codex or Claude Code) aren't affected.
  • Who can connect: anyone with remote access. Work always happens with that person's own Moodle permissions.
  • FastCGI/CGI: The bearer token is also read from REDIRECT_HTTP_AUTHORIZATION.

Teachers see their own connections under Profile › My Coursepilot connections and can revoke them there.

Site check and reverse proxy

The page Coursepilot data surface (/local/coursepilot/surface.php, requires moodle/site:config) shows the allowed tools compared with the web service surface actually registered, and checks three requirements by calling its own discovery address:

  • Public HTTPS
  • Egress: outgoing connections are possible and the response comes back.
  • PATH_INFO: the path suffix of the discovery address reaches the script. A typical pitfall: a reverse proxy or upstream service cuts it off. Fix: set AcceptPathInfo On (Apache) explicitly.

If a client can't connect even though the plugin is installed, check this page first.

Kill switch and bulk revocation

  • Kill switch: turning off Allow remote access immediately blocks any further access through the MCP endpoint. Access tokens already issued stay valid; the regular Moodle login isn't affected.
  • Revocation: The page Coursepilot connections (/local/coursepilot/admin/connections.php, requires moodle/site:config) lists all active connections on the site. Revoke them one by one or use Revoke all connections: after that, every connection has to be set up again.
  • In a security incident use both: the kill switch for new access, bulk revocation for existing tokens.

WebDAV for teachers

Teachers can keep their context area and material in their own WebDAV storage instead of Moodle (e.g. IServ, Nextcloud). They set this up themselves on their location page. You enable it once:

  1. Enable the WebDAV repository type (Site administration › Plugins › Repositories).
  2. For the WebDAV type, switch on "Allow users to add a repository instance into the user context".
  3. Give teachers the capability repository/webdav:view in their own user context, ideally through a dedicated system role.

Coursepilot checks these three points on every access and shows them as Moodle status checks.

Reverse proxy in front of the WebDAV storage (trusted_proxies): If a teacher's storage (e.g. their own Nextcloud) sits behind a reverse proxy such as Cloudflare and the proxy's IP range isn't listed in the storage's trusted_proxies, the storage sees all requests coming from a single IP. Its brute-force protection then throttles normal write access for 15–30 seconds or longer. This concerns the storage, not Moodle or Coursepilot. If you hear "the connection hangs" or "a pending change is stuck", check trusted_proxies there first. Coursepilot retries silently for only 10 seconds, so that not every write call gets delayed for everyone.

Data protection

  • No student data: The tools are on an allowlist. Submissions, forum posts, quiz attempts, grades and participant lists aren't on it. Tool names containing submission, discussion, attempt, participant, enrol, grade or user are forbidden; a contract test checks this against the surface actually registered. You can view the list on the data surface.
  • No AI calls of its own: The plugin doesn't call any AI provider. Whatever a tool returns goes to the provider of the teacher's AI client. This is also stated on the consent page every teacher sees when connecting.
  • The school is responsible. Transfer personal context data is off by default. The switch acts on the marker personenbezug: true in a context file's header, not on content: it doesn't filter names out of unmarked files.
  • External storage: Teachers are isolated from each other because the WebDAV instance has to belong to the person triggering the access. personaldatahosts is a write lock, not a read lock.
  • Moodle privacy API: Coursepilot reports its own data (OAuth connections, download tickets, pointers to previous locations) for data export and deletion. Moodle handles files in "Private files" itself.
  • Known Moodle gap: WebDAV user instances carry userid = 0 and aren't found in a GDPR data request or deletion. They store the password in plain text, so recommend app passwords to teachers.

Status checks

Moodle's system status page (/report/status/index.php) shows one check per fully described activity type ("drift") plus the WebDAV checks. Drift means a Moodle or plugin update has changed an activity type's form. Coursepilot then blocks writing for that type only; reading and all other types keep working. The page recalculates on every visit.

Language pack

The base language is English. Until translations are maintained through AMOS, a complete German translation ships temporarily with the plugin (lang/de/). The instructions for the AI (skill corpus) aren't Moodle strings and are German for now.
